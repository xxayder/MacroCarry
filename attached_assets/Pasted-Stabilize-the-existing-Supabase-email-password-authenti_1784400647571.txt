PHASE 3 — FIX DUPLICATE USERNAME HANDLING

Do not remove the database unique index. It remains the final protection against duplicate usernames.

Create a new migration file:

artifacts/mobile/supabase/migrations/002_username_availability.sql

Do not modify or rerun migration 001.

The new migration must create a narrowly scoped function for checking username availability before signup.

Required behavior:

- Function name: public.is_username_available
- Accept one candidate username.
- Trim the candidate.
- Enforce the existing format:
  - 3–24 characters
  - letters, numbers, and underscores only
- Compare usernames case-insensitively.
- Return only true or false.
- Do not return profile records, emails, user IDs, or other data.
- Use SECURITY DEFINER only if needed.
- Use SET search_path = ''.
- Fully qualify all database objects.
- Revoke unnecessary PUBLIC access.
- Grant execute only to anon and authenticated roles.
- Do not grant anonymous SELECT access to the profiles table.
- Make the migration idempotent.

Update account creation so it:

1. Validates the username locally.
2. Calls is_username_available immediately before auth.signUp.
3. If false, does not call signUp and displays exactly:
   “Username is already taken. Please choose another.”
4. If true, proceeds with signUp.
5. Keeps the unique database index as protection against race conditions.
6. If signUp returns “Database error saving new user,” check username availability one more time:
   - If the username is now unavailable, show the username-taken message.
   - If the username is still available, show a general account-creation error and preserve the real technical error in development logs.
7. Never expose raw PostgreSQL errors directly to the user.
8. Always reset the signup loading state in a finally block.

Confirm that a failed duplicate-username registration does not leave:

- an orphaned auth.users row
- a partial profiles row
- the app falsely signed in
- an infinite spinner
